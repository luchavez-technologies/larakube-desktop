# Plan 10: Windows installer (.exe) that drives a LaraKube WSL distro

**Goal:** a student on Windows downloads one normal installer, double-clicks it, and uses LaraKube Desktop like on a Mac. They never open WSL, install Linux, or run a command. The AppImage-in-WSLg route is dropped.

**Model: Docker Desktop's.** One Windows installer; the app owns a dedicated WSL distro (Docker's is `docker-desktop`; ours is `larakube-ubuntu`), imported by the app, separate from any Ubuntu the user has. The app calls into it with `wsl.exe -d larakube-ubuntu ...`. Microsoft documents the building blocks: `wsl --import <Distro> <InstallLocation> <tar>` creates a distro from a tarball (it starts as root unless `/etc/wsl.conf` sets a user), and `[boot] systemd=true` in `/etc/wsl.conf` enables systemd. Verify both against the current Microsoft docs when building; this plan was written from search results, not from running them.

## What exists and what changes

- Exists: NSIS installer config (`config/nativephp.php`), a Windows job in the release workflow, `Wsl.php` (is WSL there?), `Elevation.php` (already runs `wsl.exe -d <distro> -u root` when the app is inside WSL).
- Missing: everything that runs commands is POSIX-only. About 26 call sites in 18 files launch processes (`ClusterStatus`, `CliRunner`, `ToolLocator`, `StackCatalog`, `ToolCatalog`, `ProjectServices`, `KubeconfigDiscovery`, `FrameworkCatalog`, `DevBoxShell`, `DevBoxTunnel`, `EditorLauncher`, `LocalCluster`, `ReadinessCheck`, `CloudAuthController`, `SettingsController`, `ProjectController`, `CompanionController`, `WorkspaceCatalog`), and `ToolLocator::isolate()` wraps everything in `/bin/sh -c 'exec env -i ...'`.

## Design

1. **One executor seam.** A small `Executor` interface for "run this command here" (`run`, `start`, `readFile`, `exists`). `LocalExecutor` is today's behaviour on macOS and Linux. `WslExecutor` runs `wsl.exe -d larakube-ubuntu --user larakube --cd <dir> -- env -i ... <command>`. `ToolLocator::find()` asks the distro (`command -v`, cached) and `isolate()` returns the wrapped command. Every call site goes through it; no direct `Process::` or `ChildProcess::start` left outside the two implementations (enforced by a test that greps the app folder).
2. **Where projects live.** Inside the distro's own disk (`/home/larakube/projects`), not `C:\`. Files under `/mnt/c` are slow for `node_modules` and `vendor` and break permissions and file watching. The app shows them in Explorer as `\\wsl.localhost\larakube-ubuntu\home\larakube\projects\...`. Docker Desktop gives the same advice for the same reason. Stored paths stay Linux paths; a display helper makes the Windows form.
3. **Setup on Windows** replaces the CLI, kubectl and OpenTofu installs (they ship in the distro). Steps, resumable after a reboot: virtualization on, WSL installed (`wsl --install --no-distribution`, one elevated prompt, then a restart), rootfs downloaded with progress and checked by sha256, distro imported, `/etc/wsl.conf` written (systemd, default user), distro restarted, ready. Podman, k3s and Traefik come from the existing "Set up local development" step, run inside the distro.
4. **The rootfs.** Lives in its own repo, `luchavez-technologies/larakube-ubuntu` (public), and is built and published there, so its releases never touch Desktop's `latest` download links. Built in CI from the official Ubuntu 24.04 image: systemd, rootless Podman, the standalone `larakube`, kubectl, OpenTofu, openssh-client, git, curl, CA certificates. Provider CLIs (gcloud, aws) are installed on demand. Target under about 400 MB compressed. Published as a release asset; Desktop pins a version and a checksum. For the workshop, also hand it out as a file next to the installer so nobody downloads it on venue Wi-Fi.
5. **Local addresses.** Use the `localhost` TLD on Windows (already an allowed TLD). Browsers resolve `*.localhost` to loopback, so no Windows hosts-file edit and no admin prompt. WSL2 forwards ports listening in the distro to Windows `localhost`. This replaces the hosts-file sync and mirrored-networking work for the Desktop path. Both parts are unverified.
6. **HTTPS.** The LaraKube local CA must be trusted by the Windows browsers: import into the Windows user's trust store (no admin) from the Windows side.
7. **Windows-native conveniences come free:** open links (`Shell::openExternal`), the folder and file pickers, "Show in folder" (`explorer.exe /select,`) all work natively; the WSLg gaps disappear. Editors: VS Code through `code --remote wsl+larakube-ubuntu <path>`, with Explorer as the fallback.
8. **SSH keys and cloud logins** live inside the distro (`~/.ssh`), generated by the app, not the Windows user's own keys.
9. **Updates.** The installer updates like any Electron app. The distro does not get re-imported: `larakube update` runs inside it. A "Repair environment" action re-imports it, after warning that projects live in the distro and offering `wsl --export` first.
10. **Signing.** An unsigned installer shows SmartScreen's "unknown publisher" warning. Fine for canary testing; sign with Azure Trusted Signing (plan 04) before `v0.0.1`.

## Order

0. **Spike on a real Windows 11 machine (half a day).** Hand-build a rootfs, import it, and from a packaged `.exe` confirm: output streams live; `ChildProcess::stop` really kills the Linux process, not just `wsl.exe`; reading `\\wsl.localhost\...` works from PHP; Windows `localhost` reaches Traefik inside the distro; systemd, Podman and k3s run in an imported distro. Write the results into this plan. GitHub-hosted Windows runners probably cannot run WSL 2 (no nested virtualization; unverified), so end-to-end checks need a real machine.
1. The executor seam and the `ToolLocator` adapter, with tests (works on a Mac with a fake `wsl.exe`).
2. Rootfs build job and release asset.
3. The Windows setup flow. **Built** (`Wsl::enable/download/import`, `POST /setup/wsl/{step}`, Setup page card): turns WSL on with one administrator prompt, downloads and SHA-256-checks the image, imports `larakube-ubuntu`. Untested on real Windows; the download shows no progress bar yet.
4. Paths, projects, editors, pickers.
5. Local development: `localhost` TLD and the CA in the Windows store.
6. Installer polish, signing, updater, a Windows download page for the `.exe`, a new runbook.

## Decisions (confirmed)

- Projects live inside the distro.
- The `localhost` TLD on Windows.
- The rootfs is downloaded at first run, with an offline file for the workshop.
- Unsigned for canary, signed before `v0.0.1`.

"Rootfs" means root filesystem: the packed-up folders of a small Linux system (`/bin`, `/usr`, `/etc`, ...) with our tools already installed, as one compressed file. `wsl --import` unpacks it into a new WSL distro, so the student gets a ready LaraKube Linux without installing or configuring anything.

## Where to test

Two kinds of machine, because a machine that already has WSL hides the first-run problems:

- **A dev machine with WSL 2 already working** (the owner's Windows PC): fast iteration for the spike and for everything after the distro exists. Re-import often with `wsl --unregister larakube-ubuntu`. Install the canary `.exe` from CI instead of building the Windows app locally, which needs PHP, Node and Electron tooling on Windows.
- **A clean machine or VM, with no WSL and no Ubuntu:** the only way to test the first-run path (virtualization off, WSL missing, the reboot, a first import). A Windows 11 VM with a snapshot taken before WSL is enabled works if the host allows nested virtualization (verify); otherwise a spare laptop. Run the real first-run test here before the workshop.
  The Mac stays the main development machine: the executor seam and the tests run there; the rootfs builds in CI in its own repo. The Windows machine is the test device, not a second workspace.
